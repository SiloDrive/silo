# Plan: at-rest encryption — the sealed frame and `storage.key`

Status: **built**, except the ingest, which is `#23`. Owns the *sequence* and the decisions the issue left
open; [`../storage.md`](../storage.md) § Storage encryption, universal is
normative for the format, and where the two disagree that document wins, by
[`../roadmap.md`](../roadmap.md)'s rule.

Tracked on git.booko.info as `dkam/silo#18`, milestone `at-rest-encryption`.
Its neighbours: the ingest of existing plaintext objects is `#23`, packs are
`#17`. The issues carry state; this document carries the reasoning, and is not
updated as they close.

## Where it stands

`fileserver/objstore` has no cipher. A plain library is plaintext on disk, and
an E2EE library is the client's sealed frames on disk — which is to say the
server's own storage layer contributes nothing either way. Everything under
`store/` that says "sealed" means the *content* crypto under a library's
content key, which is a different key, a different threat model, and a
different layer from what this plan adds.

The decision recorded in § Storage encryption, universal is that the frame
does not wait for packs: a frame is self-describing whether the file holding
it contains one or a thousand, so a loose object becomes one sealed frame at
its existing path, and packs later become a container of frames plus an index
with no change to the frame or the key.

## The invariant this rests on

**`objstore`'s API speaks object bytes. A frame never escapes the package.**

That is what makes "ids and paths unchanged" true in practice rather than only
in intent, and it has four consequences that are easy to get wrong:

- `Stat` returns the **plaintext** length, not the file size. It feeds
  `ChunkStoredSize` — which is a `Content-Length` on the wire in
  `fileserver/chunks.go` — and `ObjectSize` in `fileserver/entries.go`, and it
  sizes the buffer in `objmgr.GetChunkInto`. All three become wrong by exactly
  the frame overhead if `Stat` starts answering about the file. It is derived
  as `fileSize - frameOverhead`, so `Stat` stays a single `os.Stat` and never
  opens the object. **That forces a fixed-width `ciphertext_len`**, not a
  varint: the overhead has to be a constant for the subtraction to hold.
- `List`'s `ObjectInfo.Size` is the same subtraction, from the size the
  directory walk already has in hand.
- `ReadAt` reads and opens the whole frame, then slices. GCM's tag covers the
  whole ciphertext, so there is no partial decrypt — a ranged read of a *pack*
  is a range over frames, never a range within one. Every caller today asks
  for offset zero and the full length, so nothing regresses; the doc comment
  on `ReadAt` that sells ranged reads gains the caveat.
- `WriteVerified`'s hash check moves out of `writeOpts.verify` and up into
  `objstore`: read, hash, compare, seal, hand the frame down. The order is not
  negotiable — the id names the plaintext, and verifying the ciphertext would
  verify nothing a caller asked about.

**The frame is applied above the backend seam, not inside `fsBackend`.**
§ Storage encryption, universal justifies uniform encryption partly with
*because every backend stores identical bytes — replication as plain file copy
of sealed packs*. Sealing in `objstore.Write`/`Read` makes that true of the S3
and NAS backends for free when they arrive; sealing in `backend_fs.go` means
writing it again, per backend, and having a per-backend answer to a question
the whole point was to answer once.

The cost to state plainly: Go's GCM is one-shot, so a write and a read each
hold the whole object in memory. That is nothing for a ~1 MiB chunk and is not
nothing for the 36 MB manifest of a 1 TiB file. It is accepted here. Splitting
a large object across sub-frames is a pack-format question and belongs with
`#17`, where a frame boundary is already the unit of everything.

## Decision 1 — the codec lives in `objstore`, not in `store/`

The issue says `store/frame.go`. That contradicts `store/doc.go`, which says in
as many words:

> What is deliberately not here: packs, pack indexes, storage-layer
> encryption, tiering. Those are the server's business — a pack never crosses
> the wire, so no client has any use for the code that writes one.

`store/` is the format package a client reimplements: porter-fuse imports it,
porter-mac rewrites it in Swift against `store/testdata/vectors`. No client
will ever write a storage frame, because no client will ever hold
`storage.key`. Putting the codec there would add a file to the spec surface
that every port must decide to ignore.

**So: `fileserver/objstore/frame.go`**, with golden vectors under
`fileserver/objstore/testdata/` regenerated by the same `-update` protocol
`store/vectors_test.go` established. The vectors are still worth having — they
pin a format that cannot be changed after the first byte is written — they are
simply not part of the cross-implementation contract, and `store/testdata/
vectors` should stay exactly that contract and nothing else.

The alternative was to amend `store/doc.go`. It is rejected because the rule
there is currently crisp and load-bearing, and the only thing it would buy is
matching a filename in an issue body.

The same argument places the frame's byte layout. `../storage.md` now says the
byte-level contract is not in it but in
[`../spec/store-format.md`](../spec/store-format.md), which is normative and
which § Conformance defines as the file a second implementation reproduces.
The storage frame has no second implementation and never will, so it does not
belong there either. Its layout is pinned in `../storage.md` § Storage
encryption, universal — beside the key it is encrypted under — and that section
says in one line why it is not in the spec.

## Decision 2 — the frame carries a version, and binds its header

§ Storage encryption, universal gives the frame as
`(chunk_id, ciphertext_len, nonce, ciphertext+tag)`. Two things are missing,
and both are permanent from the first frame written, because the key is
unrotatable and so the format under it is too:

1. **A magic and a version byte.** As given, a frame has no way to say "this
   is a frame" and no way to say "this is a frame of the second kind". The
   first is what makes Decision 3's fallback possible at all; the second is
   what makes a future change possible without a rewrite of everything
   everywhere, which is precisely the operation this key is defined as not
   supporting.
2. **The header as associated data.** The frame names its own `chunk_id`, and
   unless GCM authenticates that name it is decoration: nothing stops a frame
   being relabelled, or moved to another object's path, and being opened
   happily under the same key. Binding `magic ‖ version ‖ id ‖ len ‖ nonce` as
   AD costs nothing and makes the id in the header mean what it appears to
   mean.

Proposed layout, little-endian, all widths fixed:

    magic       4    "SILF"
    version     1    0x01
    chunk_id   32    the object's id — the SHA-256 of the plaintext
    ct_len      8    length of ciphertext+tag
    nonce      12    crypto/rand, fresh per write
    ct+tag      n    AES-256-GCM(storage.key, nonce, plaintext, AD=header)

`frameOverhead` is 73 bytes. Against the measured workload — ~6 million chunks
at a 1 MiB target — that is ~440 MB on ~6 TB, which is not a number worth
optimising.

The random nonce means the frame is **not** convergent: the same plaintext
written twice gives different bytes. That is correct and is the opposite of the
rule for content frames in `store/seal.go`, for the reason that rule gives —
ids are minted over plaintext, before sealing, so dedup and `changes?since=`
are untouched by what the storage layer does underneath them.

Both points are amendments to `storage.md`, made in the same change as the
code. They are not silent additions.

## Decision 3 — reads fall back to plaintext until `#23`

Ingest is out of scope here by the issue's own boundary, which leaves a window
between this landing and `#23` landing in which every object already on disk
is plaintext. Without a fallback, this change makes an existing store
unreadable on upgrade — the one migration this project claims not to need,
discovered in the one place it must not be.

So: **always write framed; on read, a file that does not begin with the magic
is opened as plaintext.** The magic plus the length arithmetic make the two
cases distinguishable without ambiguity, and a plaintext object that happened
to begin with `SILF` still fails the length check and the tag.

`#23` deletes the fallback, and the code carries a `TODO(#23)` saying so. It is
a transitional allowance with a named end, not a permanent read mode.

## One safety rule the issue does not state

**Generating `storage.key` must refuse when `storage/` already holds objects
sealed under it and no key file is present.**

A lost key that silently regenerates looks exactly like a clean first start.
The server comes up, logs its one-time "back this up now" warning, serves
requests, and the damage is found at the first read of an old object — by
which time more has been written under the new key. Cannot-lose has to be
enforced at the moment of loss, not described in a document.

The same load path refuses a key file that is not 32 bytes, and warns on
permissions looser than `0600`.

### The word "sealed" in that rule was missing, and it mattered

As first written the rule refused over a store that held *any* objects, and
that is wrong in a way only a restart shows: it collides head-on with
Decision 3. A store written before framing has objects and no key —
legitimately — and that is precisely the case the plaintext fallback exists to
carry. The refusal blocked it, so the first restart after an upgrade opened no
store at all, and the change became the migration it was designed not to be.

Three states share "no key file", and only one of them is a loss:

| on disk | what it is | what to do |
|---|---|---|
| nothing | a first start | generate |
| plaintext objects only | a pre-framing store being upgraded | generate; the fallback reads them |
| any sealed frame | the key is gone | refuse |

So the question is not whether the store is empty but whether anything in it
is a frame, which is a four-byte read per object. It stops at the first frame
found, so the case that matters most — a lost key over a sealed store — is
answered almost immediately. The case it walks to the end of is the upgrade,
once in an install's life, over a tree `#23` walks anyway.

### And it has to fail at startup, not at the first request

The key was loaded lazily, at the first `ObjectStore` opened for the first
library someone touched, which turned "this store's key is gone" into a 500 on
an ordinary request rather than a server that says why it will not run.
`objstore.EnsureKey` is called from `openStores` and from `Run`, so the
refusal happens before anything is served. `silo backup-db` deliberately does
not call it: backing up ciphertext is still worth doing, and is exactly what
someone in that state may be trying to do.

## The work, in order

1. **`fileserver/objstore/frame.go`** — `sealFrame` and `openFrame`,
   AES-256-GCM, `crypto/rand` nonce, header as AD, the `frameOverhead`
   constant, and golden vectors under `fileserver/objstore/testdata/`.
2. **`fileserver/objstore/key.go`** — `loadStorageKey(dataDir) (key []byte,
   created bool, err error)`. 32 bytes from `crypto/rand`, written `0600` and
   atomically, with the one-time warning at generation and the three refusals
   above. Cached per data directory and called from `objstore.New`, so the
   roughly a dozen construction sites need no signature change and a load
   failure lands in the `initErr` channel `objstore.New` already has for
   exactly this.

   *Landed in `objstore` rather than in a package of its own, as this plan
   first said.* A separate package cannot ask whether the store is empty
   without either importing `objstore` — which would import it back for the
   key — or spelling `"storage"` a second time. `gc` already demonstrated what
   a second spelling of a store directory costs: a renamed store turned
   `silo gc -delete` into a silent no-op that reported success. The key is
   `objstore`'s and nothing else uses it, so it lives there and `KeyPath` is
   exported for the two callers outside that need to name the file.

   The publish is temp-file-then-**link**, not rename: rename overwrites, and
   the one thing this must never do is replace a key another process created
   in the same instant. `Link` fails on an existing target, which turns that
   race into a re-read of the winner's key.
3. **Wire `objstore`**, and call `EnsureKey` at startup — seal in `Write` and
   `WriteVerified`, open in `Read` and `ReadAt`, and the size arithmetic in
   `Stat`, `List` and `Exists`.
   `Exists` keeps its "a zero-length object is absent" rule, tightened to
   "shorter than a frame is absent", which covers the same torn-write case.
4. **The read fallback** of Decision 3, with its `TODO(#23)`.
5. **Docs.** `storage.md` split into Part 1 (as built) and Part 2 (designed)
   after this plan was written, and at-rest encryption crosses that line when
   this lands — which is most of the doc work:

   - § Storage encryption, universal gains the two amendments of Decision 2,
     the frame's byte layout, the line saying why that layout is not in the
     spec, and the frame being applied above the backend seam. What remains
     designed there is the pack, not the frame, and the section says which is
     which.
   - § What Part 1 does not do loses **"Objects are stored raw, unencrypted
     and uncompressed"** — half of that sentence stops being true, and it is
     the one line in the document that a reader checks to answer this exact
     question.
   - § Key material gains `storage.key`: what it is, that it is the server's
     key and not account key material, and cannot-lose with cannot-rotate
     stated together in the one place § Storage encryption, universal requires
     them to be.
   - § Operating it, and § What is left, item 3.
   - `backup.md`'s two-kinds-of-state table, its restore section and its order
     rule; `storage.key` is the first item in the must-not-lose set and the
     table currently lists two kinds of state where there will be three.
   - The instructions `fileserver/backup.go` prints after `silo backup-db`,
     which are what an operator actually follows.
   - `roadmap.md`.

## The tests, and the order they go in

Each is written and watched fail before the code it covers. Every failure mode
here is deterministic, so there is no exception to name.

- **Frame:** round trip; tamper each of magic, version, id, length, nonce,
  ciphertext and tag, each rejected; the wrong key; a truncated frame; and the
  golden file reproduced byte for byte.
- **Key:** generated `0600` at first start; a second start reuses the same
  bytes; a missing key over a non-empty store refuses to start; a key that is
  not 32 bytes refuses.
- **`objstore`:** the assertion that actually proves encryption happened —
  write an object containing a known needle, then search the file on disk for
  it and require its absence. Then `Stat` equals the plaintext length, `List`
  agrees with `Stat`, `ReadAt` at zero returns the object, `Exists` is
  unchanged, and `WriteVerified` still rejects a mismatched id — which is the
  test that pins hashing to the plaintext rather than to the frame.
- **Fallback:** a plaintext file placed directly at a fan-out path reads back
  through `objstore` unchanged.
- **The upgrade, end to end:** a data directory holding plaintext objects and
  no key opens, reads them, and seals what it writes from then on. Verified
  against the real binary as well: a first start generates and warns, a
  restart is silent, a pre-framing store starts, and a sealed store with no
  key refuses by name and writes nothing.
- **The regression proof for "ids and paths unchanged":** the existing
  `fileserver/objstore/objstore_test.go` and
  `fileserver/encrypted_library_test.go` pass with no edits at all. An edit
  needed in either is the signal that the seam leaked, and is to be treated as
  a finding rather than as test maintenance.

  **One edit was needed, and it is the honest kind.** `testExists` asserted
  `os.Stat` on the object's file was exactly 130 bytes — reaching past the
  seam to the disk, which is the one thing this change alters. It now asserts
  both halves: `Stat` says 130 and the file says `130 + frameOverhead`. The
  pair is a better test than the original, and nothing else in either file
  moved. `TestListYieldsEveryObjectWithItsSize` and
  `TestReadAtPastTheEndReportsEOF` were the two most likely to break and both
  passed untouched, which is the seam holding.
- **The second wrap:** an E2EE chunk's bytes on disk differ from the frame the
  client uploaded, while `GetChunk` returns that client frame exactly. This is
  the one test that shows the two layers are actually two.

Then `make check`.

## What this does not do

Not here, deliberately: the ingest that rewrites existing plaintext objects as
frames (`#23`), packs and pack indexes (`#17`), any durable tier, and any
change to what crosses the wire. Nothing above alters an id, a path, a
response body or a manifest.

One consequence worth naming rather than discovering: the one-time generation
warning fires per data directory, so a `go test ./...` run prints it once per
temporary store. That is the warning working, not a leak — but if it ever
becomes noise worth suppressing, suppress it in the tests and never in the
server.
